## 三、开发工作流

### 安装依赖

```bash
npm install
```

### 启动开发模式

```bash
npm start
```

等价于 `node scripts/build-renderer.js && electron .`

**每次改完前端代码都要重新跑**，因为渲染层是预打包的。

### 调试

- **渲染层**：菜单「视图 → 开发者工具」（`Ctrl+Shift+I`）
- **主进程**：启动命令加 `--inspect`，用 Chrome 访问 `chrome://inspect`

### 改完重新提交渲染层

```bash
node scripts/build-renderer.js
```

## 四、打包发布

### Windows

```bash
npm run pack:win
```

产出到 `.cache/build/`：
- `轻墨 Setup 1.1.0.exe` — NSIS 安装包
- `轻墨 1.1.0.exe` — 便携版
- `win-unpacked/` — 解包目录（调试用，不分发）

发到 `dist/windows/`：

```bash
npm run pack:win
cp .cache/build/*.exe dist/windows/
```

### macOS

#### 情况 A：在 mac 上打（推荐，能出 .dmg）

```bash
npm run pack:mac
```

产出 `.dmg`，体验最好。

#### 情况 B：在 Windows 上交叉打（只能出 .zip）

`.dmg` 需要 macOS 的 `hdiutil`，无法交叉。但 `.app` 的 zip 可以：

```bash
npm run mac:fetch      # 首次运行，下载 Electron mac 运行时
npm run pack:mac-x     # 组装并压缩
```

产出到 `.cache/build/mac/`：
- `轻墨-1.1.0-mac-arm64.zip` — Apple Silicon
- `轻墨-1.1.0-mac-x64.zip` — Intel

发到 `dist/macos/`：

```bash
cp .cache/build/mac/*.zip dist/macos/
```

#### 清理缓存

每次 mac 打包会在 `.cache/mac-build/` 留下几百 MB 的临时解包目录：

```bash
npm run cache:clean          # 只删临时目录，保留运行时（推荐）
npm run cache:clean -- --all # 连运行时一起删，回收约 195MB
```

运行时缓存路径由 `fetch-runtime.js` 里的 `CACHE` 常量决定，
默认 `<项目>/.cache/electron-mac/`，已 gitignore。

### ⭐ mac 产物必须验结构（Windows 上看不出来的问题）

**交叉打包是「逐条改 ZIP 条目」，任何一条分支写漏了，产出的包在 mac 上就是打不开的**，
而在 Windows 上完全看不出来（zip 照样能解、文件照样能读）。

```bash
npm run verify:mac          # 校验 release/macos 里最新的 zip
npm run verify:mac -- 路径.zip
```

**24 项检查**，覆盖：

| 类别 | 检查什么 | 抓过的 bug |
| --- | --- | --- |
| 目录结构 | 只有一个 `.app`、叫 `QingMo.app`、无 `Electron.app` 残留 | Info.plist 改写分支提前 return，没走整体改名 → 包里出现孤立的 `Electron.app/Contents/Info.plist` |
| 可执行文件 | `Contents/MacOS/QingMo` 存在、无 `Electron` 残留 | 同上 |
| 资源 | `app.asar` / `icon.icns` 存在，无 `electron.icns` / `default_app.asar` 残留 | — |
| Info.plist | `CFBundleExecutable` = `QingMo`、**与实际可执行文件名一致**、`CFBundleName` = 轻墨、`CFBundleIdentifier`、`CFBundleIconFile` | 改写分支被 `startsWith('Electron.app/')` 拦截 → 成了死代码，`CFBundleExecutable` 一直是 `"Electron"` |
| asar 内容 | bundle 含 `toggleLinePrefix` / `standalone` | 打进旧 bundle |
| ZIP 结构 | 条目总数 = **255**（与官方包一致）、符号链接 >= 10、`Versions/Current` 是符号链接 | 条目丢失 |

**`CFBundleExecutable` 与实际可执行文件名不一致 = mac 上双击完全没反应，且没有任何报错。**
这是最隐蔽也最致命的一个，两者必须一致。

**关于符号链接的检查方式**：不能靠「解压后看是不是链接」——
Windows 的 `unzip` 不支持符号链接，解出来必然丢。
`verify-mac.js` 直接读 ZIP 的中央目录，看条目的 external attributes 里
有没有 `S_IFLNK`（`0xa000`）标志。

#### transform 里的分支顺序（踩过的坑）

```js
// ✅ 顺序：精确匹配的特殊条目 → 整体改名 → 其余原样复制
if (name === 'Electron.app/Contents/Info.plist') { ... }   // 改内容 + 改名
if (name === 'Electron.app/') return { rename: 'QingMo.app/' };
if (name.startsWith('Electron.app/')) return { rename: ... };  // 会 return！
```

**两条铁律**：

1. **任何「提前 return」的分支都要放在整体改名之前**，否则它下面的处理就是死代码。
2. **提前 return 的分支必须自己给 `rename`** —— 它走不到整体改名那步了。
   只给 `data` 的话，文件会留在原路径（`Electron.app/...`），
   产出的目录结构就是乱的。

**还有第三点**：判断 Info.plist 要用**精确匹配**，不能用 `endsWith`。
包里有 **9 个 Info.plist**（主 app + 4 个 `Electron Helper*.app` + 4 个 framework），
而 Helper 的 plist 里**根本没有 `CFBundleExecutable` 键** ——
用 `endsWith` 会把 Helper 的也匹配上。

#### Info.plist 要改的键

| 键 | 值 |
| --- | --- |
| `CFBundleName` | 轻墨 |
| `CFBundleDisplayName` | 轻墨 |
| `CFBundleExecutable` | QingMo（**必须与实际文件名一致**）|
| `CFBundleIdentifier` | cn.bajiaolu.qingmo |
| `CFBundleShortVersionString` | 1.6.2 |
| `CFBundleVersion` | 1.6.2 |
| `CFBundleIconFile` | icon.icns |
| `LSApplicationCategoryType` | public.app-category.productivity |

`build-mac.js` 改完后会**自校验** `CFBundleExecutable`，不一致直接抛错中止构建。

**三条硬限制**（这是为什么需要自建管线）：

| 限制 | 现象 | 应对 |
| --- | --- | --- |
| electron-builder 平台检查 | `Build for macOS is supported only on macOS` | 不用它，手动组装 |
| Windows 自带 tar 拒绝 mac zip | `This does not look like a tar archive` | 自写 `unzip.js` / `zip.js` |
| `fs.cpSync` 中文路径崩溃 | 进程强杀 `0xC0000409` | 手写 `readdirSync` + `copyFileSync` |

### 跨平台发行说明

Windows exe 未签名（需付费证书），mac app 未签名 + 未公证（需 $99/年开发者账号）。
两者首次打开都需要用户手动放行，这是个人项目的现实取舍。

### 预览区直接编辑（`live-edit.js`）

用户在预览区直接打字，改动实时写回 Markdown 源码。

**核心机制：块级映射**

```
Markdown 源码
   │
   ├─ marked.lexer(md) ──→ [token0, token1, token2, ...]
   │                       每个 token 带 .raw（精确的源码片段）
   │                       token.raw 顺序拼接 === 原文
   │
   ├─ 渲染成 HTML ──────→ <h1> <p> <ul> ... （与 token 一一对应）
   │
   └─ 用户在预览区改字 ──→ elementToMarkdown(el) ──→ 新 Markdown
                            ↓
                     只替换源码里那一个区间
                     （CodeMirror transaction）
```

**为什么能做到精确替换**：`marked.lexer()` 切出来的 token，
每个的 `.raw` 拼接起来**严格等于原文**（`dev/scripts/test-live-edit.js`
里有一条断言专门守这个）。所以只要知道「第几个顶层元素」，
就知道它对应源码的哪一段字符区间，改完再拼回去就行。

**关键实现细节**：

| 点 | 说明 |
| --- | --- |
| space token 要保留 | 空行分隔符（`type: 'space'`）不产生 DOM，但**必须**留在切分结果里 —— 漏掉会导致回写时吃掉段落间的空行，把文档结构改坏 |
| `skip` 标记 | space token 标 `skip: true`，渲染时跳过、映射时不计数 |
| 块级回写 | 用户改第 N 个块 → 只替换 `blocks[N]` 的区间，其余内容和 CodeMirror 光标由它自己维护，不会跳动 |
| 转换失败就不改 | `elementToMarkdown` 抛异常时放弃这次回写。**宁可不改，也不能把文档改坏** |
| 勾选任务列表 | `change` 事件捕获 checkbox，转回 `[x]` / `[ ]` |
| 粘贴 | `preventDefault` + `insertText`，只取纯文本 |
| 链接 | `preventDefault` + `window.open`，不打断预览 |
| 渲染前净化 | 回写时读的是 `innerHTML`，而 `innerHTML` 是 `DOMPurify.sanitize` 之后的产物，所以没有 XSS 风险 |

**局限（有意为之）**：粒度是块，不是字符。在预览区改字时，
整块的 Markdown 会被重新生成 —— 行内标记（`**粗**`、`[链接](...)`）
能保留，但不做逐字符级别的还原。这也是为什么在预览区**不能插结构**：
插标题/表格请用工具栏按钮，或切到源码模式。

**第三层（`verify-edit.js`）是唯一能测到「用户实际点按钮」这层逻辑的**。
前两层测的是 `live-edit.js` 的纯函数，而命令层（`wrap` / `insertTable` /
`toggleLinePrefix` / `heading`）的 bug 只有真窗口里才暴露。

它抓到过的真 bug：嵌套格式互相破坏、表格空行列数写死、多行选区越界。


**为什么必须有两层**：`elementToMarkdown` 的 20 多个标签分支（列表嵌套、任务列表、
表格、引用、代码块）只在真实 DOM 里才跑得到。第一版只有 Node 测试，
结果上线后被发现：有序列表编号全错（双加 1）、嵌套有序列表缩进用两格、

### ⭐ 编辑内核（`editor-core.js` / `editor-keys.js`）

编辑区的「语法感知」逻辑抽成了两个**纯函数模块**，不碰 DOM 也不碰 CodeMirror：

| 文件 | 职责 |
| --- | --- |
| `editor-core.js` | Markdown 语法识别（行前缀、强调区间、表格行）+ 块级插入的位置计算 |
| `editor-keys.js` | Enter / Backspace / Tab 的行为规划（算出「该做什么」，不直接改文档） |

**为什么要抽出来**：

1. 这些逻辑是「操作各类语法」的核心，之前散在 `app.js` 里，
   只能靠真窗口黑盒测试，定位一条要跑好几分钟。
2. 抽成纯函数后**毫秒级**就能验证，`npm run test:core` 70 项不到 1 秒。

**已实现的手感**（**大部分是 CodeMirror 原生就有的**，见下面的警告）：

| 按键 | 行为 | 谁实现的 |
| --- | --- | --- |
| 列表项 Enter | 续同级列表；有序列表编号递增 | **CodeMirror 原生** |
| 空列表项 Enter | 结束列表 | **CodeMirror 原生** |
| 引用 Enter | 继续 `> ` | **CodeMirror 原生** |
| Backspace 删标记 | 删光标**左边**的标记 | **CodeMirror 原生** |
| 列表 Tab | 变子项 | **CodeMirror 原生**（indentMore）|
| **表格 Tab** | **跳到下一格；末格按 Tab 加一行** | **我们补的**（原生没有）|

### ⚠⚠ 别抢 CodeMirror 已经实现的行为

`@codemirror/lang-markdown` **自带**一套 Markdown 专用绑定（源码 399-400 行）：

```js
{ key: "Enter",    run: insertNewlineContinueMarkup }
{ key: "Backspace", run: deleteMarkupBackward }
```

而且是 `Prec.high` 优先级 —— 比我们自己的 `keymap.of` **更高，先跑**。

**之前自己又实现了一遍 Enter/Backspace，等于用粗糙版本去覆盖它**，后果：

- 它不懂代码块 / HTML 区域（原生会正确地不处理）
- 拆分点处理不一样
- 一旦用 `Prec.high` 去抢，`preventDefault()` 会**打断 IME 选词**

**教训**：加按键绑定前，先翻 `node_modules/@codemirror/lang-markdown/dist/index.js`
看原生提供了什么。**只补它没有的**（目前只有表格 Tab 跳格）。

原生 Backspace 的语义也是标准的那样 —— 删**光标左边**的字符：
光标紧挨标记右边（`- |列表项`）→ 删标记；光标在行首（标记右边）→ 左边没东西，不动。

### ⚠⚠ 中文输入法（IME）会咬人

`view.composing` 的定义是 `inputState.composing > 0`，而 `composing` 是在
**文本上屏**时才 ++ 的（0 → 1）。所以：

| 阶段 | `view.composing` | 结果 |
| --- | --- | --- |
| IME 候选框（还没上屏） | **false** | CodeMirror 的保护失效 |
| 已上屏的组合 | true | 保护生效，按键放行 |

**所以「用 Enter 选词」在候选框阶段可能被吃掉**，用 Space 选词不受影响。
这是上游既有行为（v1.3.0 也一样），不是我们引入的。

**不要用 `Prec.high` 抢 Enter 来"修"它** —— `preventDefault()` 可能让
所有 IME 的选词都失效，比现状更糟。

我们自己加的 handler（表格 Tab）保留了 `v.composing || lastKeyIsComposing` 检查：
IME 期间按 Tab 放行。`lastKeyIsComposing` 来自 contentDOM 上**捕获阶段**的
keydown 监听（`event.isComposing || event.keyCode === 229`）——
因为 `view.composing` 在候选框阶段是 false，光看它不够。

**加新语法行为的三步**：

1. 在 `editor-core.js` 加识别函数（如 `parseXxx`）
2. 在 `editor-keys.js` 的 `planEnter` / `planBackspace` / `planTab` 里加分支
3. 在 `scripts/test-editor-core.js` 加断言 → 在 `tests/syntax/run-keys.js` 加真机用例

**两个必须注意的细节**：

- **拆分点不能早于标记末尾**。光标在 `- ` 的空格处按 Enter 时，
  如果就地拆行，原行会变成 `-`（尾空格被吃掉），
  而 `-` 后面没空格在 Markdown 里就不是列表项了。
- **块级插入要落在块边界**。Markdown 的块由空行分隔，
  插到光标处会把段落劈成两半（`这是引` + ` ``` ` + `用内容`）。
  `planBlockAfter` 负责算对插入点。

### ⭐ 界面改造（2026-10-25）

这轮改了七处，每一处背后都有个具体原因：

| 改动 | 原因 |
| --- | --- |
| 深浅色按钮移到第二行末尾 | Windows 的原生窗口按钮占着第一行右侧，按钮被挤到中间，不像「行末尾」 |
| 标题栏去掉 logo | 窗口标题栏已经显示应用名，左上角再放一遍是重复 |
| 加「清除格式」图标 | 选中一段带格式的文字只能一个标记一个标记地取消 |
| 深色模式行号列不再是白条 | 见下面「CSS 变量名对不上」 |
| 深色模式光标改成白色 | 蓝色光标在深底上不够醒目 |
| 插入图片弹窗（本地 / 远程） | 原来只插一个 `![图片描述](https://)` 占位，URL 还得手改 |
| 无序/有序/任务三者互相切换 | 原来点「任务列表」在无序行上会**把列表删掉** |

**⚠ 三个必须记住的坑**

**① CSS 变量名对不上**

`app.js` 的 `EditorView.theme` 里写的是 `var(--fg)` / `var(--bg)` / `var(--fg-dim)`，
但 `common.css` 里定义的色阶叫 `--c-0` / `--c-900` …。
**那四个变量从来没定义过** → `var()` 解析失败 → 整条声明作废 →
编辑器拿到的颜色是「空」，CodeMirror 内置的 light 主题就接管了。

结果就是深色模式下：行号列是白条、光标是黑色。

现在 `common.css` 里补了别名：

```css
--fg:       var(--c-900);
--fg-dim:   var(--c-500);
--fg-faint: var(--c-400);
--bg:       var(--c-0);
--caret:    var(--c-900);      /* 深色下改成 #ffffff */
```

**② CodeMirror 内置主题的特异性比我们的高**

内置主题里有：

```js
"&light .cm-gutters":         { backgroundColor: "#f5f5f5" },
"&light .cm-activeLineGutter":{ backgroundColor: "#e2f2ff" },
"&light .cm-activeLine":      { backgroundColor: "#cceeff44" },
```

`&light` 会编译成 `.ͼlight .cm-gutters`（两个 class），
比我们的 `.cm-gutters`（一个 class）**特异性更高** → 我们的样式被盖掉。

解法是提高一级：`.cm-editor .cm-gutters`。

```css
.cm-editor .cm-gutters { background: var(--c-25); ... }
.cm-editor .cm-activeLineGutter { background: transparent; }
.cm-editor .cm-activeLine { background: transparent; }
.cm-editor .cm-cursor, .cm-editor .cm-dropCursor { border-left-color: var(--caret); }
```

**③ 弹窗显隐不能靠 opacity 过渡**

原来 `.modal-mask { opacity: 0 }` + `.modal-mask.show { opacity: 1 }`，
靠 CSS 过渡淡入。**但窗口未激活时 Chromium 会暂停 CSS 过渡** ——
opacity 就永远停在 0，弹窗整个透明（内容却能"透"出来，因为没有背景色）。

现在改成：遮罩立即可见（背景色生效），入场动画交给 `.modal` 的 transform。
就算 transform 过渡也没跑，弹窗只是差 8px 位移，照样能用。

### ⭐ 版本更新（检查 + 自动更新）

**检查更新**：查 GitHub Releases 的 latest tag，跟当前版本比。
主进程 `app:checkUpdate` → `GET api.github.com/repos/engrecho/qingmo/releases/latest`。

**三个必须知道的点**：

① **有新版 ≠ 当前平台能下载到新版**

v1.5.0 / v1.5.1 的 Release 当时只发了 mac 的资源，Windows 用户检查更新会看到
「发现新版本 v1.5.1」，点下载却跳到 release 页面 —— 里面一个 `.exe` 都没有。

所以返回结果分三个字段：

| 字段 | 含义 |
| --- | --- |
| `hasUpdate` | 有新版本**且**当前平台有对应资源 → 可以直接更新 |
| `newerExists` | 有新版本（不管当前平台有没有） |
| `platformReady` | 当前平台是否有对应资源 |

② **GitHub API 匿名请求 60 次/小时会限流**

装机量一大必然撞上 403。原来直接报「检查失败」，用户还以为没有新版本。

现在有**降级路径**：改用 `github.com/.../releases/latest` 的 302 重定向，
从 `Location` 头里取 tag（`/releases/tag/v1.5.1`）—— 不走 API，没有限流。
降级时只拿得到版本号（拿不到资源列表），所以 `degraded: true`。

③ **自动更新（Windows）**

走 `electron-updater` 的 `autoUpdater`，流程是：检查 → 下载 → 静默安装 → 重启。

**三个前提，缺一个就静默失败**：

| 前提 | 说明 |
| --- | --- |
| **必须是 NSIS 安装版** | portable（免安装）没有升级通道。靠 `process.env.PORTABLE_EXECUTABLE_FILE` 判断 |
| **Release 上必须有 `latest.yml`** | electron-updater 不是翻资源列表，而是去读 `latest.yml`（版本号、文件名、sha512、blockmap 地址） |
| **文件名必须和 yml 一致** | yml 里的 `path` 是 electron-builder 生成时的原始名。发布脚本改名了就会 404 |

为此：

- `package.json` 的 `build.publish` 配了 GitHub provider（不配 electron-builder 不生成 yml）
- `nsis.artifactName` 固定成 ASCII 名 `QingMo-${version}-win-setup.exe`
  （`latest.yml` 里的 path 和 Release 里的资源名必须一致）
- `release.js` 现在**会传 `latest.yml`**（之前明确排除，说「不对外发」—— 那是错的）
- `publish.js` 同步产物时**会带上 `latest.yml`**，并校验 yml 里的 path 在 `release/windows/` 里真实存在

**macOS 不做自动更新**：需要 Apple Developer 证书（$99/年）+ 公证，
否则 Gatekeeper 会拦下自动下载的 app（用户还得手动右键打开）。
mac 上只做「检查更新 + 引导下载」。

**验证**：

```bash
npm run verify:auto-update    # 校验 latest.yml 与产物一致性（sha512/size/path）
npm run test:update           # 版本比较 + 平台资源匹配
npm run test:update-fallback  # 降级路径（302 解析）
npm run test:auto-update      # 真机跑一次 checkForUpdates
```

**开发模式下的坑**：

- electron-updater 在未打包时**直接跳过检查**（`application is not packed`），
  会返回空 —— 代码要如实报「开发模式不检查更新」，不能当成「已是最新」
- 它只在 `app.getAppPath()` 下找 `dev-app-update.yml`。
  正常 `npm start`（`electron .`）时就是 `dev/` ✓，
  但跑 `scripts/` 下的测试脚本时是 `dev/scripts/` —— 所以 `build-renderer.js`
  会自动从 `dist/latest.yml` 生成一份 `dev-app-update.yml`（派生产物，不入库）
- 强制走真实配置：`QINGMO_FORCE_UPDATE=1`

### ⚠⚠ 诊断日志的 IPC 失败会造成死循环

**这是「编辑器完全打不了字」的真正原因**（实测：20 次异常 → **8856 次** IPC 报错）。

死循环路径：

```
report()  →  api.reportLog() 的 Promise 拒绝
          →  unhandledrejection
          →  又触发 report()
          →  又拒绝  →  ……
```

渲染进程被无限上报打满，编辑器就卡住没反应了。

**必须做的两件事**（`src/renderer/logger.js`）：

1. **catch 住 Promise 拒绝** —— `api.reportLog()` 返回的是 Promise，
   直接扔掉就会变成未捕获拒绝
2. **连续失败到上限就停止上报** —— `failStreak >= MAX_FAIL` 直接 return

```js
if (failStreak >= MAX_FAIL) return item;
const p = api.reportLog({ ... });
if (p && typeof p.catch === 'function') p.catch(() => { failStreak++; });
```

回归测试：`npm run test:log-loop`（故意不注册 IPC handler，压 20 次异常，
断言 IPC 报错 < 50 次、渲染进程还活着、还能编辑）。

### ⭐ 诊断日志

**为什么加**：用户反馈「有时候双击 md 打不开」—— 而原来的代码里
所有失败路径都是 `return false`，一个字都不留，用户和开发者都无从判断。

| 位置 | 内容 |
| --- | --- |
| `src/main/logger.js` | 主进程日志。落在 `userData/logs/qingmo-YYYY-MM-DD.log` |
| `src/renderer/logger.js` | 渲染进程异常上报（`window.onerror` + `unhandledrejection`） |
| `src/main/file-assoc.js` | Windows 文件关联的检查与修复 |

**记了什么**：

- 启动 header：版本 / Electron / Chrome / Node / 平台 / 架构 / 可执行文件路径 / 启动参数
- 文件打开的**每一步和每种失败原因**（扩展名不支持 / 文件不存在 / 读失败 / 窗口未就绪已暂存）
- 窗口创建失败、渲染进程崩溃、页面加载失败、preload 失败
- 预览渲染异常（带文档片段）
- live-edit 的 DOM→Markdown 转换失败（带块索引、原文、HTML 片段）
- 渲染进程上报的未捕获异常（带堆栈）

**用户怎么用**：

- 菜单「帮助 → 导出诊断日志…」→ 复制到剪贴板 + 打开日志文件夹
- 关于弹窗底部有「诊断」区块，直接显示**文件关联状态**，
  以及「修复文件关联」按钮

**「双击 md 打不开」的常见原因**：

| 原因 | 怎么确认 |
| --- | --- |
| 装的还是旧版本（`fileAssociations` 是 v1.5.0 才加的） | 日志里「文件关联检查」段显示 `.md 关联: md_auto_file` |
| 关联被别的软件抢走（Typora / VS Code / Obsidian） | 同上，`.md 命令` 显示的是别的 exe |
| 用户从没运行过安装版（portable 不注册关联） | 同上 |
| 文件扩展名不在白名单 | 日志里「扩展名不支持」 |

修复走「帮助 → 修复文件关联」，写的是 **HKCU（用户级），不需要管理员权限**。

> ⚠ 菜单栏已在 Windows 上撤掉（页面上的图标按钮覆盖了全部功能）。
> 上面提到的「帮助 → …」入口，现在都在**标题栏右边的齿轮图标（设置面板）**里。
> macOS 保留原生菜单。

## 六、本机环境坑位

这几个在特定环境下会反复遇到，提前知道能省很多时间。

### 1. `ELECTRON_RUN_AS_NODE=1` 污染

某些 IDE 内置终端（VSCode / WorkBuddy 等）会注入这个环境变量，
导致 Electron 退化成纯 Node 解释器，报错长这样：

```
TypeError: Cannot read properties of undefined (reading 'getPath')
TypeError: Cannot read properties of undefined (reading 'handle')
```

**解法**：运行前清掉

```bash
env -u ELECTRON_RUN_AS_NODE node ...
```

`run.bat` 已经处理了。

### 2. `require('util').stderr` 是 undefined

这个 Node 构建里 `util.stderr` 不存在，
所以 `process.stderr.write(util.format(...))` 会**第一行就崩**，
表现为「脚本跑起来毫无输出」。

**用 `console.error(util.format(...))` 代替。**

### 3. 管道会吞子进程输出

```bash
node build.js | tail -20        # ❌ 什么都看不到
node build.js 2> log.txt         # ✅ 落盘再看
```

### 4. `fs.rmSync` 批量删除触发安全守卫

删除超过 50 个文件会报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。

**解法**：用时间戳目录，不要反复清理同一个目录。

```javascript
const STAMP = String(process.hrtime.bigint()).slice(-9);
const dir = path.join(BUILD, 'stage-' + STAMP);
```

### 5. `fs.cpSync` 在中文路径下崩进程

退出码 `0xC0000409`（STATUS_STACK_BUFFER_OVERRUN），无任何报错。

**解法**：手写递归

```javascript
function copyDir(src, dst) {
  fs.mkdirSync(dst, { recursive: true });
  for (const e of fs.readdirSync(src, { withFileTypes: true })) {
    const s = path.join(src, e.name), d = path.join(dst, e.name);
    if (e.isDirectory()) copyDir(s, d);
    else if (e.isFile()) fs.copyFileSync(s, d);
  }
}
```

### 6. `@electron/asar` 只能用 CLI

它是 ESM-only，且 CJS 的 `createPackageWithOptions` 在某些版本会**静默不产出文件**（不报错但文件不存在）。

```javascript
// ✅ 可靠
execFileSync(process.execPath, [
  path.join(SRC, 'node_modules/@electron/asar/bin/asar.mjs'),
  'pack', srcDir, outFile
]);
```

### 7. Windows 自带 tar 拒绝 mac zip

```bash
tar -xf electron-darwin-arm64.zip    # ❌ This does not look like a tar archive
```

mac 应用的 zip 有特殊标记，libarchive 不认。用 `scripts/mac/unzip.js`。

### 8. Git Bash 的 `/tmp` ≠ Node 的 `/tmp`

`curl -o /tmp/x.json` 写的路径，Node `require('/tmp/x.json')` 找不到（解析成 `C:\tmp\x.json`）。

跨工具传文件用工作区内相对路径。

### 9. 云盘同步目录会独占锁住 `.asar`

**这个项目位于 `C:\Users\Administrator\Documents\云电脑同步\` 下，
而这个目录被极空间（ZSpaceSync）和天翼云盘（CtyunDesktopMaster）实时同步。**

这些同步客户端为了保证一致性，会**独占打开**它监控列表里的文件
（`.asar` 恰好在内）。后果：

```
mv: cannot move '.cache/build' to '.cache/trash/build': Permission denied
rm -f app.asar: Device or resource busy
```

表现为：文件能读能复制，但**不能删除、不能改名、所在目录也不能改名**。
进而 `electron-builder` 清空输出目录时直接失败：

```
⨯ remove ...\resources\app.asar: The process cannot access the file
  because it is being used by another process.
```

**排查方法**（按顺序）：

```bash
# 1. 逐文件试探，找出被占用的
node -e "const fs=require('fs');try{const fd=fs.openSync('路径','r+');fs.closeSync(fd);console.log('可写')}catch(e){console.log('被占用')}"

# 2. 更准的探测（openSync 不带 share mode，检测不到独占，要用改名）
node -e "const fs=require('fs');try{fs.renameSync('路径','路径.tmp');fs.renameSync('路径.tmp','路径');console.log('可改名')}catch(e){console.log('被占用')}"
```

**解决办法**（按推荐顺序）：

| 方案 | 说明 |
| --- | --- |
| **① 把项目移出云盘目录** | 最彻底。移到 `D:\Projects\Qingmo` 之类，同步客户端不监控就不会锁 |
| ② 用 `pack:win:safe` | 打包时自动探测占用并换新目录（已内置） |
| ③ `robocopy /E /MOVE` | 能搬走 99.9%，只剩锁住的那一两个文件 |
| ④ 暂停同步客户端 | 结束 `ZSpaceSync.exe` / `CtyunDesktopMaster.exe` 进程 |

**排查时不要用 `Add-Type` 编译 .NET 代码调 Restart Manager API** ——
本环境会拦截（`Add-Type compiles and loads .NET code at runtime`）。

**⚠ 还有一种更隐蔽的表现：不报错，直接卡死。**

2026-10-25 打包 v1.6.0 时遇到：`pack:win:safe` 跑了 23 分钟没结束，
`app-builder` 进程 20 秒内 **CPU 增长 0.00s、IO 增长 0.0 MB** —— 纯粹挂起。

症状特征：
- `dist/win-unpacked/` 里 Electron 运行时已经复制完（71 个文件 / 268MB），
  但 **`resources/` 目录压根没建**
- `app-builder.exe` 进程挂着，CPU/IO 全零
- 没有报错，没有超时，就是不动

**同样卡在写 `resources/app.asar` 那一步** —— 和上面的「文件被占用」是同一个根因，
只是这次不是报 `EBUSY`，而是同步驱动的句柄让写操作无限等待。

**可靠的解法：在云盘目录之外打包，再把产物拷回来。**

```bash
# ① 建本地临时工作区（源码只有 4MB，node_modules 用 npm install 重装）
mkdir -p /c/qm-build
# 复制 dev/（排除 node_modules）
# ② 装依赖（走 npm 缓存，比复制 591MB 快）
cd /c/qm-build/dev && npm install
# ③ 在这里打包
node scripts/build-renderer.js && npm run pack:win:safe
# ④ 产物拷回 dist/
```

实测这样打包一路顺畅，**没有卡住**。

### 10. 删除操作被安全守卫拦截

`unlink` / `rm` 会报：

```
[safe-delete][SAFE_DELETE_FAIL_CLOSED] {"reason":"trash-failed", ...}
```

不是文件被占用，是环境的安全 hook 拦的。**用「挪到 `_to_delete/`」代替删除**，
`renameSync` 不受该 hook 影响。

同理，删除失败后 Windows 会把目录改名成 `xxxX` 之类的残留名，
产物里就会混进垃圾 —— 所以 `publish.js` 里统一用 `moveAway()` 而不是 `unlink`。

### 11. bundle 与源码不同步 → 改了一堆代码却「完全没效果」⭐

**这个坑最隐蔽，也最浪费时间。**

`app.bundle.js` 是 esbuild 产物，`.gitignore` 排除了它、不入库。
而 `index.html` 引用的是 **bundle**，不是 `app.js` 源码。

所以：**改了 `app.js` 而忘了重新构建，页面跑的就是旧代码**。
更糟的是 `index.html` 是入库的、会被改动 —— 于是 **HTML 和 JS 版本不匹配**，
症状是「各种说不清的怪 bug，而且列举不出来」。

**真实案例**：v1.4.0 和 v1.5.0 连续两个版本都踩了。
两个版本都改了 `app.js`（标题栏重构、列表作用行首、预览区失焦修复），
但**没有一个 commit 包含重新构建的 bundle**。
用户实际跑的一直是 v1.3.0 的界面 + 旧逻辑，
新版声称修的 bug 一个都没生效。

**已加的防线**：

| 位置 | 措施 |
| --- | --- |
| `npm start` / `npm run dev` | 本来就有 `build:renderer` ✅ |
| `dev/run.bat` | **已补** `npm run build:renderer`（原来直接 `npx electron .`） |
| `scripts/mac/build-mac.js` | **已补** 开头重建（原来会把旧 bundle 打进 mac 包） |
| `scripts/pack.js` | 本来就有 ✅ |
| 手动检查 | `npm run check:bundle` —— 比对 mtime，过期就报错 |
| 自动修复 | `npm run check:bundle -- --fix` |

**改了渲染层代码后的自检**：

```bash
cd dev
npm run check:bundle        # 先确认 bundle 是新的
npm run test:all            # 25 + 92 + 45 = 162 项
```

### 12. 嵌套格式会互相破坏（`wrap` 的包裹判断）

点「加粗」再点「斜体」，**粗体会被吃掉**，文档从 `**文字**` 变成 `*文字*`。

**根因**：`wrap()` 判断「是否已包裹」时只取前 N 个字符：

```js
const beforeText = view.state.sliceDoc(from - before.length, from);
if (beforeText === before && afterText === after) { /* 取消包裹 */ }
```

文档是 `**文字**`（粗体），选区正好是「文字」。
点斜体时 `before='*'`，`beforeText` 取到的是粗体 `**` 的**第二个 `*`**，
判定成「已经斜体了」→ 走取消分支 → 粗体被吃掉。

**修复**：包裹必须是**独立**的 —— 标记的前后不能再是同类标记字符。

```js
const charBefore = beforeStart > 0 ? view.state.sliceDoc(beforeStart - 1, beforeStart) : '';
const charAfter  = (to + after.length) < docLen ? view.state.sliceDoc(to + after.length, to + after.length + 1) : '';
const standalone = !charBefore.includes(before[0]) && !charAfter.includes(after[0]);
if (beforeText === before && afterText === after && standalone) { /* 取消 */ }
```

**教训**：判断「前后缀」时，不能只看紧邻的 N 个字符 ——
它们可能是**更大包裹的一部分**。要检查边界。

### 13. 表格选区当表头时空行列数写死

`insertTable()` 有选区时，空数据行硬编码成 `|  |  |`（**两列**），
但表头可能是三列 → 生成列数不齐的表格，Markdown 渲染时错位。

**修复**：空行按表头列数生成。

```js
const emptyRow = '| ' + head.map(() => ' ').join(' | ') + ' |';
```

## 七、常见开发问题

### 界面改了但没生效

渲染层是预打包的，改完 `app.js` / `style.css` / `index.html` 要重新构建：

```bash
node scripts/build-renderer.js
```

### 打包报 `EnsureEmptyDir` / `EnsureDir` 失败

**先看坑位 9** —— 大概率是云盘同步锁住了 `app.asar`。

用安全版打包命令，它会自动避开：

```bash
npm run pack:win:safe
npm run pack:mac:safe
```

### 校验打包产物是否正常

```bash
npm run verify:asar -- ../.cache/build/win-unpacked/resources/app.asar
```

会提取 asar 里的 `main.js`，检查语法并验证关键正则的行为。

### 截图核对设计

渲染层支持走查参数：

```bash
# 用 Edge 无头截图
msedge --headless=new --screenshot=out.png --window-size=1440,900 \
  "file:///path/to/index.html?shot=1&theme=dark"
```

| 参数 | 作用 |
| --- | --- |
| `shot=1` | 注入演示文档 |
| `theme=light\|dark` | 强制主题，跳过 localStorage |

> 走查页需 mock `window.api`（Electron preload 不存在时 `api.on` 会抛异常中断启动代码）。

### 依赖体积

`@codemirror/language-data` 包含全部语言语法，让 bundle 到了 2.9MB。
只需要 Markdown 高亮的话可以删掉它，`markdown()` 不传 `codeLanguages` 即可。

### 修改版本号

`package.json` 的 `version` 字段，同时影响：
- Windows 安装包文件名
- mac zip 文件名
- 应用内「关于」信息
- mac 的 `Info.plist`（`build-mac.js` 自动读取）
