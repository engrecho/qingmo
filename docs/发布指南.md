# 轻墨发布指南

## 1. 本地生成安装包

更新 `dev/package.json`、`dev/package-lock.json` 版本，维护 RELEASE_NOTES.md。先运行对应回归，再执行 `npm --prefix dev run build:renderer`。

Mac 上构建 Apple 芯片版本：

```bash
cd dev
env -u ELECTRON_RUN_AS_NODE CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --mac --arm64 --dir --publish never --config.electronDist=node_modules/electron/dist
codesign --force --deep --sign - ../dist/mac-arm64/轻墨.app
codesign --verify --deep --strict ../dist/mac-arm64/轻墨.app
env -u ELECTRON_RUN_AS_NODE npx electron-builder --mac --arm64 --prepackaged ../dist/mac-arm64/轻墨.app --publish never
```

若 7-Zip 生成 ZIP 失败，可在仓库根目录执行 `ditto -c -k --norsrc --noextattr --keepParent dist/mac-arm64/轻墨.app dist/轻墨-1.6.7-mac-arm64.zip`，之后仍须运行 Mac 结构与签名校验。

Windows x64 在 Mac 上交叉构建时，需要 Windows Electron 运行时（项目缓存为 `.cache/electron-win/runtime`）：

```bash
env -u ELECTRON_RUN_AS_NODE npx electron-builder --win --x64 --publish never --config.electronDist=../.cache/electron-win/runtime
```

Windows 主机可直接执行 `npm run pack:win`。构建完成后，在 dev 下执行 `npm run publish:mac`、`npm run publish:win` 将交付同步至 release；Mac 校验脚本会检查结构与签名。删除旧安装包和无用中间文件，保留最终 release 文件。

## 2. 发布 GitHub Release

发布前将本次源码提交并推送到远程分支，确保标签与构建源码一致。安装 GitHub CLI，并先执行 `gh auth login` 登录有仓库写权限的账号。

下面以 v1.6.7 为例，在仓库根目录运行。Mac 上传名必须使用 ASCII：将本地 `轻墨-1.6.7-mac-arm64.dmg/zip` 复制到临时目录并重命名为 `QingMo-1.6.7-mac-arm64.dmg/zip`。Windows 文件名保持不变。将本次发布说明写入临时 `notes.md`。

```bash
gh release create v1.6.7 --repo engrecho/qingmo --target 已推送的分支名 --title '轻墨 1.6.7' --notes-file 临时目录/notes.md --draft
gh release upload v1.6.7 临时目录/QingMo-1.6.7-mac-arm64.dmg 临时目录/QingMo-1.6.7-mac-arm64.zip release/windows/QingMo-1.6.7-win-setup.exe release/windows/QingMo-1.6.7-win-portable.exe release/windows/latest.yml --repo engrecho/qingmo
```

先保留草稿，确认五个文件上传完成、远程大小和 SHA256 与本地一致，再正式发布：

```bash
gh release edit v1.6.7 --repo engrecho/qingmo --draft=false --latest
gh release view v1.6.7 --repo engrecho/qingmo --web
```

发布页为 https://github.com/engrecho/qingmo/releases 。更新程序依赖 Release 资产 API 的 digest（SHA256），必须确认 GitHub 返回该值。Mac 自动更新使用对应架构 DMG；Windows 使用 setup.exe。`latest.yml` 提供旧版本兼容；不要将 portable.exe 填入其 path。上传完成后删除临时上传副本。

仅有 Apple 芯片包时，在说明中明确标注，不能把它作为 Intel 版本发布。当前 Mac 包为本地临时签名，未进行 Apple 公证。

## 上传较慢时

可分别使用独立的 `gh release upload` 进程上传各文件，并仅在这些进程中设置 `GODEBUG=http2client=0`，避免多个大文件共用 HTTP/2 连接影响速度。v1.6.7 使用 4 个独立上传进程完成分发，上传后仍逐一比对 GitHub API 返回的大小和 SHA256，再将草稿正式发布。不需要修改系统代理或全局环境。

## GitHub Actions 原生打包

`.github/workflows/release.yml` 在 main 的 dev/package.json 变化时运行，也支持手动触发。macOS 与 Windows 原生构建、执行相关回归；Mac Apple 芯片包执行本地签名及结构校验，PDF 在 Mac 验证。两端成功后才创建 Release 草稿，上传 5 个文件，比对大小与 SHA256，并校验 latest.yml 的安装包路径和 SHA512，随后正式发布。任一环节失败不会正式发布。

此流程不包含 Apple Developer ID 签名或公证，不会解决 Gatekeeper 的未公证提示。发布已存在的版本前应先检查对应 Release 状态，禁止覆盖已发布资产。

Mac 的文件关联图标复用应用 `icon.icns`。electron-builder 25 会先复制应用图标，再复制文档关联图标；若两者显式指定同一文件，会发生 `EEXIST` 硬链接冲突。Windows / Mac 的 fileAssociations 分别配置，Windows 保留显式 ICO 路径，Mac 省略 icon 以使用应用图标。


### 复用已验证产物继续发布

若双端 build 均成功、只有 release 步骤失败，可手动触发 `publish.yml`，输入原始构建 run_id。它会检查两个 build job 均成功，使用该次构建的完整源码 SHA 和已上传产物，不重新打包。仅复用目标 SHA、文件大小和 SHA256 一致的草稿资产，拒绝覆盖已发布版本或不匹配的草稿。

草稿在 tag 尚未创建时，`GET /releases/tags/<tag>` 可能返回 404。必须通过 releases 列表取得草稿的数字 ID，按 `/releases/<id>` 校验和发布，不要将 404 当成不存在而反复创建草稿。确认精确 5 个资产、大小和 SHA256，以及 latest.yml 的安装包路径和 SHA512 后才发布。

v1.6.8 的双端产物由 run `40536209722` 构建，run `40537719232` 完成上述校验与正式发布。Mac 仅本地签名，未公证。

手动运行 release.yml 时默认 `publish=false`，双端回归与构建通过后，将校验后的安装包放入带 run_id 的临时 preview 草稿，不影响 latest 正式版。确认包已下载并校验后可清理本次临时草稿；正式发布仍使用正常版本标签。main 的版本变化仍按正式发布流程执行。

v1.6.9 已合入 PR #2 并发布。合入后的应用、依赖、图标与回归脚本与构建源码 `82a24f9` 一致，因此复用 run `40543434697` 的原生验证产物。重新比对五个本地文件与草稿的大小、SHA256 及 latest.yml 的 SHA512 后，按数字 Release ID 将已验证 preview 草稿改为 v1.6.9 并发布为 latest；未重复构建或重新上传不同的安装包。
